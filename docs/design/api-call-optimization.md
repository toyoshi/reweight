# Design Doc: OpenAI API呼び出し最適化

**日付**: 2026-02-19
**ステータス**: 実装済み

## 背景と課題

フィードを19本に拡充した結果、1回の実行で取得する記事数が約332件に増加した。
従来の2段階方式（スクリーニング1回 + 個別スコアリング最大30回 + 個別要約10回 = 約41回）では、コストと実行時間の両面で問題が顕在化していた。

### 定量的な問題

| 指標 | 値 |
|------|-----|
| 記事数 | ~332件/回 |
| API呼び出し | ~41回/回 |
| 主なコスト源 | 個別スコアリング30回（全体の73%） |

## 意思決定

### 決定1: スクリーニングにgpt-4o-miniを採用

**Why**: スクリーニングは「タイトル一覧から候補を選ぶ」という単純なタスク。タイトルだけを見て判断するため、高い推論能力は不要。gpt-4o-miniでも品質は落ちにくい。

**トレードオフ**: gpt-4o-miniの判断精度が若干劣る可能性はあるが、スクリーニングは「広く拾う」フェーズなので、多少の漏れ・ノイズは後段のスコアリングで補正される。コストは約1/15に削減される。

**却下した案**: スクリーニング自体を廃止する案。332件全件をスコアリングすると34バッチ必要になり非現実的。

### 決定2: スコアリングをバッチ化（10件/回）

**Why**: 1記事1APIコールは非効率。10件分のスコア+理由程度であればレスポンスサイズは問題にならない。

**バッチサイズ10の根拠**:
- 5件: バッチ数が多くなり削減効果が薄い
- 10件: コンテキスト内に十分収まり、各記事への注意が維持される
- 20件: レスポンスが長くなりすぎ、後半の記事のスコアリング精度が落ちるリスク

### 決定3: スコアリングと要約を1パスで統合

**Why**: スコアリング時に記事を読んでいるので、そのまま要約も生成すれば追加コストはトークン量の増分のみ。API呼び出し回数は0になる。

**トレードオフ**: Top10以外の20件分の要約は使われず無駄になる。しかし、要約は短文（2-3文）なのでトークンコストは小さく、API呼び出し10回削減の効果のほうがはるかに大きい。

**フォールバック**: Summarizerクラスは残し、バッチ処理で要約が欠落した記事がある場合に個別要約する。

## 結果

| フェーズ | Before | After |
|---------|--------|-------|
| スクリーニング | gpt-4o x 1回 | gpt-4o-mini x 1回 |
| スコアリング | gpt-4o x 30回 | (統合) |
| スコアリング+要約 | - | gpt-4o x 3回 |
| 要約 | gpt-4o x 10回 | フォールバックのみ |
| **合計** | **~41回** | **~4回 (90%削減)** |

## 変更されたファイル

- `lib/reweight/progress_judge.rb`: バッチスコアリング+要約の統合実装
- `lib/reweight/summarizer.rb`: フォールバック専用に変更（要約済み記事をスキップ）
- `bin/generate`: Step 2で要約も完了、Step 3はフォールバックのみ

## リスクと緩和策

| リスク | 緩和策 |
|--------|--------|
| バッチ内の後半記事の精度低下 | バッチサイズ10に抑え、各記事に十分な注意が行くようにする |
| gpt-4o-miniのスクリーニング漏れ | 最大30件と余裕を持たせ、後段のスコアリングで精度を担保 |
| バッチAPIコールの部分失敗 | rescue句でバッチ単位のエラーハンドリング。Summarizerがフォールバック |
| JSON構造が崩れる | response_format: json_objectを指定し、構造化出力を強制 |
